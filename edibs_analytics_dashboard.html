Cálculo de ROAS, CPA, CVR
# Fact table unificada fact = ads.merge(campaigns, on='campaign_id') fact = fact.merge(sales_agg, on=['campaign_id','date']) # Métricas base fact['ROAS'] = fact['revenue_usd'] / fact['ad_spend_usd'] fact['CPA'] = fact['ad_spend_usd'] / fact['conversions'] fact['CVR'] = fact['conversions'] / fact['clicks'] fact['CTR'] = fact['clicks'] / fact['impressions'] # ROAS dinámico por cliente def dynamic_roas(df, group_by): g = df.groupby(group_by).agg( revenue=('revenue_usd','sum'), spend=('ad_spend_usd','sum')) g['ROAS'] = g['revenue'] / g['spend'] return g # CPA ajustado por escala de canal avg_imp = channel['impressions'].mean() channel['CPA_adj'] = channel['CPA'] * ( channel['impressions'] / avg_imp) # LTV estimado (3.5 compras promedio) client['LTV'] = client['avg_order_value'] * 3.5

📊 Estructura BBDD
Revenue no vinculado directamente a cliente
La tabla Sales solo tiene campaign_id y product_id. Para calcular revenue por cliente se requiere un JOIN indirecto vía Campaigns. Esto introduce riesgo de error en análisis ad-hoc sin documentación adecuada.
Join de 3 tablas
🔧 Problemas Detectados en la BBDD Original + Propuestas de Mejora
🔴
Sin tabla de hechos unificada
Sales y Ads son tablas separadas sin una clave de unión directa. Los KPIs como ROAS requieren JOINs complejos y propensos a errores cuando los equipos hacen consultas ad-hoc.
→ Crear FACT_AD_PERFORMANCE con revenue, spend, conversions en la misma granularidad (campaign × date)
🟡
Canal como string sin normalizar
El canal está almacenado como texto libre en Campaigns ("LinkedIn", "Facebook"...). Sin FK a una tabla de dimensión, un error de tipeo como "linkedin" rompe los agrupamientos silenciosamente.
→ Crear DIM_CHANNEL con channel_id como PK y FK en Campaigns. Añadir constraint de integridad.
🟡
Sin tabla de fechas / calendario
Las fechas están en formato string en múltiples tablas. Esto dificulta análisis temporales (semana vs fin de semana, festivos, comparativas YoY) sin lógica adicional en cada query.
→ Crear DIM_DATE con year, quarter, month, week, is_weekend, is_holiday. Pre-calcular en ETL.
🟢
Granularidad inconsistente en Sales
Sales tiene filas duplicadas de (campaign_id, date, product_id): múltiples registros por combinación sin un sale_id primario. Esto genera ambigüedad en agregaciones COUNT vs SUM.
→ Añadir sale_id como surrogate key. Documentar si cada fila es 1 transacción o un agregado diario.
🟣
Sin campos de auditoría / metadata
Ninguna tabla tiene campos created_at, updated_at, data_source o ingestion_batch. En entornos multi-fuente (CRM + Ads APIs + Email), la trazabilidad de datos es crítica para debugging.
→ Añadir created_at, updated_at (TIMESTAMP) y source_system (VARCHAR) a todas las tablas.
🔵
Retainer mensual no aprovechado
El campo monthly_retainer_usd existe en Clients pero no se usa en ningún cálculo de rentabilidad. El verdadero ROI para la agencia incluye el retainer como ingreso, no solo el ad spend del cliente.
→ Crear vista AGENCY_PROFITABILITY: (retainer + margin_on_spend) - operational_cost por cliente.
